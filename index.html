01 — CONCEPTOS CLAVE

¿Qué significa desacoplar?

Separar responsabilidades y definir límites claros para que un componente no dependa de los detalles internos de otro.

01

Frontend y backend independientes

La interfaz presenta la experiencia al usuario; el backend aplica las reglas del negocio y gestiona los datos. Pueden desarrollarse y desplegarse por separado mientras respeten un contrato compartido.

02

Comunicación mediante contratos

Los servicios colaboran sin compartir su implementación interna. REST usa recursos HTTP; gRPC ofrece llamadas tipadas y eficientes; los eventos notifican cambios de forma asíncrona.

03

Escalabilidad independiente

Cada componente puede desplegarse y escalar según su carga. Si el servicio de pedidos recibe más tráfico, es posible aumentar sus instancias sin escalar todo el sistema.

04

Database per Service

Cada microservicio es dueño de sus datos y los expone a otros mediante su API, en vez de compartir tablas. Esto reduce el acoplamiento, aunque requiere resolver consistencia y consultas entre servicios.

i

Idea importante: microservicios no significa “dividir por dividir”. Cada servicio debe representar una responsabilidad del negocio y tener límites que el equipo pueda operar.

02 — DOS ENFOQUES

Monolito vs. microservicios

No hay una arquitectura universalmente mejor: la elección depende del dominio, el equipo y las necesidades operativas.

Comparación entre arquitectura monolítica y arquitectura de microservicios
Aspecto Arquitectura monolítica Arquitectura de microservicios
Estructura Una aplicación con componentes integrados. Servicios pequeños organizados por capacidades del negocio.
Despliegue Normalmente se publica la aplicación completa. Cada servicio puede publicarse de forma independiente.
Escalabilidad Se escala la aplicación como una unidad. Se escala cada servicio según su demanda.
Datos Es común una base de datos compartida. Cada servicio controla su propio almacenamiento.
Complejidad operativa Menor para comenzar y operar. Mayor: requiere observabilidad, automatización y gestión de fallos de red.

03 — EN LA PRÁCTICA

Independencia con responsabilidad

Separar servicios da flexibilidad, pero también distribuye la complejidad. Para que el sistema sea confiable, cada límite debe tener contratos y observabilidad claros.

1

Define contratos estables

Versiona APIs, valida compatibilidad y acuerda qué datos se intercambian.

2

Asume fallos parciales

Usa límites de tiempo, reintentos controlados e idempotencia en operaciones críticas.

3

Observa el sistema completo

Centraliza métricas, registros y trazas para entender las llamadas entre servicios.
